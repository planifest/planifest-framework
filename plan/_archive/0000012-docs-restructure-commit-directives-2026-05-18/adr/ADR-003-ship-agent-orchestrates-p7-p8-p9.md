## Context

With the introduction of P9 (ADR-002), the orchestrator needs a strategy for invoking the close-out phases (P7, P8, P9). Three options exist: the orchestrator calls each phase skill directly in sequence; the ship-agent owns all three; or a new dedicated close-out agent is introduced. The choice affects how many top-level orchestrator calls the close-out requires, and which skill is responsible for sequencing the assessment and shipping steps.

---

## Decision

The ship-agent owns the complete close-out sequence. The orchestrator makes a single call to the ship-agent, which:

1. Executes **P7 Archive**: changelog, skips, `plan/current/` archive, `.feature-id`, commit
2. Spawns **build-assessment-agent** as a sub-agent for **P8**, passing the archived build-log path; waits for the report
3. Executes **P9 Ship**: git tag, push/PR decision, PR description or `gh pr create`

The ship-agent emits the correct phase prefix (`P7:`, `P8:`, `P9:`) as it moves through each step, so the human sees clear phase transitions.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Orchestrator calls P7, P8, P9 skills separately | Full orchestrator visibility; clear separation | Orchestrator becomes a thin loop with no added value; close-out logic split across three invocations | Rejected — the orchestrator's role is pipeline sequencing, not sub-step sequencing within the close-out |
| New close-out agent owns P7+P8+P9 | Clean separation from ship-agent | Adds a new skill file; ship-agent becomes vestigial | Rejected — unnecessary complexity; ship-agent already owns shipping concerns |
| Ship-agent owns P7+P9; orchestrator calls P8 directly between them | Explicit P8 boundary | Awkward: orchestrator must wait for ship-agent to complete P7, then call P8, then re-invoke ship-agent for P9 | Rejected — breaks the single-invocation model and creates handoff complexity |

## Consequences

**Positive:**
- Single orchestrator call for the entire close-out — less complexity at the orchestrator level
- Phase transitions (P7→P8→P9) are visible to the human via prefixes without requiring three separate orchestrator invocations
- build-assessment-agent retains its focused responsibility; ship-agent owns the sequencing

**Negative:**
- The ship-agent skill file is now more complex — it describes three phases rather than one
- A bug in the ship-agent's P7 section could prevent P8 and P9 from running

**Risks:**
- If the ship-agent fails mid-sequence (e.g. after P7 but before P8), the orchestrator has no automatic recovery path — the human must manually invoke the remaining phases
