# ADR-005 - No automatic retry on setup failure

## Context

REQ-006 defines what happens when the re-invoked `setup.sh`/`setup.ps1` fails partway through, after `CLAUDE.md`/`AGENTS.md` have already been deleted (ADR-001). At this point the repo is in a degraded state (boot files missing) until setup completes successfully. A retry could plausibly be attempted automatically, since the confirmed flags and attempted command are already cached (ADR-002), and the failure may be transient (a momentary file lock).

## Decision

The skill never retries automatically. On failure, it stops immediately, investigates what it can about the cause (lock, permission, held-by-process), reports the setup script's own output, the step reached, and the exact attempted command as a copyable code block, and leaves the cached flags/command in `.claude/.planifest-setup-flags` (ADR-002) for a human-initiated retry.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Retry automatically a fixed number of times with backoff | Recovers transparently from transient failures (e.g. a momentary file lock) | Repeated automatic re-invocation of a script that mutates the filesystem, without the human on the loop seeing what happened between attempts, obscures what state the repo actually ended up in | The failure investigation (cause of lock/permission) is only useful if the human on the loop actually sees it before anything is attempted again; automatic retry would either skip that reporting or repeat it silently in a loop |
| Retry automatically only for a specific, narrow class of transient errors (e.g. file lock, not permission) | Narrower blast radius than blanket auto-retry | Requires the skill to reliably classify failure causes into "safe to retry" vs "not", which the investigation step (REQ-006) can inform but not guarantee; a misclassified permission error retried automatically wastes the human's time silently | The investigation is best-effort, not authoritative; treating its output as a retry-safety classifier overstates its reliability |
| No investigation of cause at all, just report the raw setup output | Simpler to implement | Leaves the human on the loop to diagnose lock/permission issues themselves from raw script output, exactly the manual reverse-engineering burden this feature exists to remove | The human on the loop explicitly asked for cause investigation to be added to the error-path draft during Scope Lock review (build-log.md) |

## Affected Components

| Component | Impact |
|-----------|--------|
| `planifest-refresh-setup` | REQ-006 implements the stop-investigate-report sequence with no retry loop; a retry is a fresh invocation of the skill, not a code path within a single run |

## Consequences

**Positive:**
- The human on the loop always sees exactly what happened before anything is attempted again, no state changes occur silently between a failure and a retry
- Simpler failure handling: no retry-count state, no backoff logic, no partial-success bookkeeping across attempts

**Negative:**
- A genuinely transient failure (e.g. a lock released a second later) still requires the human on the loop to re-invoke the skill manually rather than resolving itself

**Risks:**
- None beyond the inconvenience already accepted above; the cached marker file (ADR-002) means a manual retry does not repeat detection, keeping the cost of manual retry low
