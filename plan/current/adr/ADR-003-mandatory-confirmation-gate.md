# ADR-003 - Mandatory human confirmation gate regardless of reconstruction confidence

## Context

The original backlog entry (`0000013-setup-refresh-skill-preserving-settings`) framed the skill as removing manual reverse-engineering work. It would be tempting to let the skill proceed automatically when its flag reconstruction is high confidence, since that is the common case once `.claude/.planifest-setup-flags` exists (REQ-002/ADR-002). This is a convenience-versus-safety trade-off: automatic proceed on high confidence saves one interaction per refresh, but removes the last check before an irreversible deletion (ADR-001) and a re-invocation of `setup.sh`/`setup.ps1` with flags that change install behaviour.

## Decision

The skill always halts for an explicit human affirmative before REQ-004's deletion step, in every run, regardless of whether every flag was reconstructed at high confidence from the marker file or inferred at lower confidence from hook wiring. The confirmation prompt always shows the full flag set, its source (marker vs inferred), confidence per flag, and the exact command about to run (REQ-003).

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Auto-proceed when every flag is high confidence (sourced from the marker file) | Fewer interactions for the common, already-installed case | The one scenario this removes the check for is exactly the scenario ADR-002 makes routine (a marker file existing), so most runs would silently skip the only safety check before an irreversible action | Removes the confirmation gate for the majority case, defeating REQ-003's purpose |
| Confirmation only on the first run per session, silently reuse for subsequent runs | Convenient for repeated refreshes in one session | A stale confirmation from an earlier state in the session could be silently applied to a changed flag set | No mechanism to detect "the flags changed since last confirmation" without re-showing them, so this degrades to the same review burden with an added staleness risk |
| Confirmation only when confidence is below a threshold | Balances convenience and safety | Introduces a threshold value that has to be chosen, tuned, and explained; a wrong threshold silently reintroduces the risk this ADR closes | The Scope Lock Challenge's confirmed answer (build-log.md, P0) was explicit: never proceed automatically on low confidence, and the same reasoning extends to high confidence, since confidence reflects signal quality, not stakes |

## Affected Components

| Component | Impact |
|-----------|--------|
| `planifest-refresh-setup` | Implements the confirmation gate as a hard stop before REQ-004, in every code path, with no bypass flag |

## Consequences

**Positive:**
- No run, regardless of confidence, can delete a boot file or re-run setup without the human on the loop having seen the exact command first
- Simple to reason about and test: one gate, no conditional bypass logic to get wrong

**Negative:**
- Every refresh costs one confirmation interaction, even for the routine, high-confidence, already-installed case

**Risks:**
- An inattentive human on the loop could rubber-stamp a wrong high-confidence flag without reading it; this ADR does not eliminate that risk, it only guarantees the opportunity to catch it exists (R-004 in the risk register)
