# ADR-001 - Hardcoded, non-extensible deletion allowlist

**Skill:** [adr-agent](../../../planifest-framework/skills/planifest-adr-agent/SKILL.md)
**Tool:** claude-code
**Model:** claude-sonnet-4-6
**Feature:** 0000020-setup-refresh-skill
**Component:** planifest-refresh-setup
**Status:** accepted
**Date:** 2026-08-01

## Context

`planifest-refresh-setup` needs to delete `CLAUDE.md` and `AGENTS.md` before re-invoking `setup.sh`/`setup.ps1`, because those two scripts will not overwrite boot files that already exist. This is the one place in the feature where the skill performs an irreversible, destructive filesystem action. REQ-004 requires that `settings.local.json` and every other user-owned file are never touched, under any circumstance.

## Decision

The deletion allowlist is a hardcoded constant listing exactly `CLAUDE.md` and `AGENTS.md`. It is not read from configuration, not derived from a glob pattern, and not extensible by a flag, environment variable, or user input at runtime. If a future feature needs to delete a different or additional file, that requires a new ADR and a code change to the constant itself, not a configuration change.

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Glob pattern (e.g. delete any file matching `*.boot.md`) | Flexible, covers future boot files without code changes | A misconfigured or overly broad pattern could match a user-owned file; harder to audit at a glance | The safety requirement (R-001, high impact if the allowlist is ever widened by mistake) outweighs the flexibility gain |
| Configurable list (flag or config file naming which files to delete) | Lets the human on the loop or a future tool integration extend the list without a code change | Moves a safety-critical decision into user-supplied input, which is exactly the surface REQ-004 exists to close off | Configurability is the attack surface this feature is designed to eliminate, not preserve |
| Derive the list from what `setup.sh`/`setup.ps1` would regenerate (introspect the scripts) | Self-updating if the scripts change what they write | Couples a safety boundary to script internals that can change independently; a script refactor could silently widen the deletion set | Too indirect for a safety-critical boundary; the allowlist should be visible and reviewable in one place, not inferred |

## Affected Components

| Component | Impact |
|-----------|--------|
| `planifest-refresh-setup` | Implements the constant and the deletion step (REQ-004); the constant is the single source of truth for what may ever be deleted |

## Consequences

**Positive:**
- The deletion boundary is auditable at a glance, one constant, no configuration surface to reason about
- Removes an entire class of misconfiguration risk (a human or agent accidentally widening the deletion set)

**Negative:**
- Adding a new boot file type in a future feature requires a code change and a new ADR, not just a config update, this is a deliberate cost, not an oversight

**Risks:**
- If a future contributor "fixes" this by making the list configurable without re-reading this ADR, the safety property is lost silently; mitigated by R-001 in the risk register and a dedicated validate-agent test (per REQ-004's acceptance criteria) that fails if the allowlist is ever parameterised
