# ADR-008 - Cross-Model Review Gate Sits at End of P6, Strictly Before P7 Archive

## Context

The pre-ship review needs a reviewer with different blind spots from the maker, and its fix loop (implement→review→fix) must be able to edit the implementation. The original research brief placed this "before P9" — but P7 already archives and deletes `plan/current/`, and the ship-agent's Hard Limit forbids touching code after archive. A gate between P7 and P9 would review work it is forbidden to fix. (Risk R-003, corrected at P0.)

---

## Decision

The gate runs at the **end of P6, before any P7 archive action begins**. Orchestrator control flow makes the ordering structural: the ship-agent (P7) is only invoked after the gate reports approval (or the toggle is off). The reviewer is a fresh-context subagent (per ADR-006) on a different model id than the implementer, resolved from the Model Tier table; the verdict records both model ids. On approval → proceed to P7. On findings → fix loop per loop-runner (cap 3, no-progress halt); cap without approval blocks P7 and escalates to the human with outstanding findings. Toggle `cross_model_review`, default off.

---

## Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------|------|------|-------------|
| Between P7 and P9 (brief's original wording) | Reviews the "final" state | Post-archive: fix loop would violate the archive lock; plan/current/ already gone | Structurally self-contradictory (R-003) |
| Inside P4 validate | Reuses existing loop | P5 security and P6 docs changes would ship unreviewed | Gate must see the complete diff |
| Replace the human PR review | One review to rule them all | Removes the human from the highest-stakes gate | Loops harden what reaches the human; they never replace the human |

## Consequences

**Positive:**
- The fix loop always operates on live, editable state; the archive lock is never challenged
- Different-model review gives the final gate genuinely different failure modes from the maker

**Negative:**
- Full-diff second-model reviews are the most token-expensive loop in the feature (bounded by cap 3, measured by P8)

**Risks:**
- Model-id availability varies by tool — if no second id is resolvable, the gate degrades to same-model fresh-context review and records the degradation in the verdict (assumption A-004)
