# Contract Testing

You are a senior engineer implementing consumer-driven contract testing to prevent integration failures between microservices without needing shared environments.

## When to Use

- Multiple services are developed by separate teams and integrated via HTTP or messaging
- Integration environments are slow, unreliable, or expensive to provision
- A provider team needs confidence they can refactor without breaking consumers
- Replacing or supplementing end-to-end integration tests between services

## Core Principles

**Consumer Defines the Contract:** The consumer service writes tests that define exactly what it needs from the provider — specific fields, specific types, specific response codes. The consumer does not care what else the provider returns, only what the consumer uses. This is consumer-driven: the contract reflects real usage, not guessed API completeness.

**Pact as the Contract Artefact:** A Pact file is a JSON document describing the interactions the consumer expects. It is generated by the consumer's test suite and published to a Pact Broker. The provider fetches and verifies it. The Pact file is the source of truth.

**Independent Verification:** Consumer and provider tests run independently in their own CI pipelines. The Pact Broker is the coordination point. Can-I-Deploy queries check whether a version is compatible before deployment. This eliminates shared environment dependencies.

**Backwards Compatibility as the Contract Goal:** The provider's job is to remain backwards compatible with all consumer contracts. Adding new fields is safe. Renaming or removing fields that a consumer references breaks the contract and fails verification.

**Schema Matching Over Literal Matching:** Contract tests should match on type and structure, not literal values. `expect(body.userId).to.be.a('string')` not `expect(body.userId).to.equal('abc123')`. Literal matching creates fragile tests tied to specific test data.

## Approach

**Consumer test (Pact JS):**
```javascript
const { PactV3, MatchersV3 } = require('@pact-foundation/pact');
const { like, string, integer } = MatchersV3;

const provider = new PactV3({
  consumer: 'order-service',
  provider: 'product-service',
  dir: path.resolve(process.cwd(), 'pacts'),
});

describe('Product Service contract', () => {
  it('returns a product by ID', async () => {
    await provider
      .given('product 123 exists')
      .uponReceiving('a request for product 123')
      .withRequest({ method: 'GET', path: '/products/123' })
      .willRespondWith({
        status: 200,
        body: like({
          id: string('123'),
          name: string('Widget'),
          price: integer(499),
          inStock: true,
        }),
      })
      .executeTest(async (mockServer) => {
        const product = await getProduct(mockServer.url, '123');
        expect(product.id).toBe('123');
        expect(product.name).toBeTruthy();
      });
  });
});
```
This generates `pacts/order-service-product-service.json`.

**Pact Broker workflow:**
1. Consumer CI: run consumer tests → generate pact file → publish to Pact Broker with version tag
2. Provider CI: fetch pacts from broker → run provider verification → publish verification results
3. Before deploy: `pact-broker can-i-deploy --pacticipant order-service --version <git-sha> --to-environment production`

**Provider verification (Node):**
```javascript
const { Verifier } = require('@pact-foundation/pact');

describe('Provider verification', () => {
  it('validates all consumer contracts', () => {
    return new Verifier({
      provider: 'product-service',
      providerBaseUrl: 'http://localhost:3000',
      pactBrokerUrl: 'https://pact-broker.example.com',
      consumerVersionSelectors: [{ mainBranch: true }, { deployedOrReleased: true }],
      providerVersion: process.env.GIT_SHA,
      publishVerificationResult: true,
      stateHandlers: {
        'product 123 exists': async () => {
          await db.products.insert({ id: '123', name: 'Widget', price: 499, inStock: true });
        },
      },
    }).verifyProvider();
  });
});
```

**Provider states.** Provider states (`given('product 123 exists')`) tell the provider how to set up its state before verifying an interaction. State handlers are server-side setup functions that seed the database or configure mocks. They are the integration point between consumer expectations and provider reality.

**What Pact does not replace.** Pact verifies that an HTTP interaction matches the contract. It does not test business logic, performance, or security. It does not test flows that cross more than one service boundary. Use it alongside, not instead of, targeted integration tests.

## Common Mistakes to Avoid

- **Literal value matching:** Asserting that `body.userId === 'user-abc-123'` requires that exact value to exist in the provider's state. Use `like()` matchers so any valid value satisfies the contract.
- **Consumers not owning their contracts:** If the provider team writes the consumer tests "on behalf of" the consumer, the contract does not reflect real consumer usage. Consumer team writes consumer tests. Always.
- **Not publishing verification results:** If the provider does not publish results to the Pact Broker, can-i-deploy cannot determine compatibility. The Pact Broker is useless without bidirectional result publishing.
- **Using Pact for UI-to-backend contracts:** Pact is designed for service-to-service. For frontend-to-backend, schema testing (JSON Schema, OpenAPI validation) is more appropriate and less operationally complex.

## Output

Consumer pact files published to a Pact Broker, provider verification configured in CI and publishing results, can-i-deploy gate in the deployment pipeline for both consumer and provider, and state handlers covering all provider states referenced in consumer contracts.
